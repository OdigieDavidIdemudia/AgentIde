AgentIde
REFERENCE IMPLEMENTATION

Measuring what endpoint security actually stops

A security product's own dashboard tells you what it detected. It does not tell you what it missed. AgentIde is a framework for finding the second half — running a defined set of adversary techniques against an endpoint and scoring which ones the installed EDR/XDR actually caught.

Dual-use tooling

This framework installs a hardened system service, attempts to disable installed security products, and terminates vendor processes in order to measure resilience. It is destructive by design. Run it only on systems you own or have written authorisation to test. Unauthorised use of this tooling may breach computer-misuse law and employment terms.

01

The problem

Vendor marketing is built on detection counts. A console full of green telemetry is self-reported by the product under evaluation, and a detection is not the same claim as a prevention. Two products can both show "blocked" for the same technique while behaving completely differently at the edges — one ignores the credential-theft path entirely, the other survives it.

Nobody had a way to ask the uncomfortable question on a consistent basis: run the same technique against every product, and tell me plainly which ones I would not have caught.

02

Architecture

Three layers. The agent executes technique modules and reports results; the dashboard aggregates, scores and reports; the design layer holds the assessment definitions themselves so a standard can change without a recompile.

  • agent/Go. Runs as a Windows service or Linux daemon, or interactively from the CLI. Discovers installed security vendors, executes assessment modules, streams every result back over a WebSocket.
  • dashboard/Node.js and React. Aggregates results across the estate, scores findings against ATT&CK techniques, and generates narrative assessment reports.
  • design/The assessment standard itself as data — which techniques run, how they are weighted, how a pass is defined. Separating this from the code means the standard is reviewable on its own.
03

How an assessment runs

Passive or active. In passive mode the dashboard drives the agent by command, which is what makes the interaction itself an observable event — an EDR that reacts to being driven remotely is revealing something. Active mode runs a scripted profile unattended.

  1. Deploy the agent — installed as a service with a bootstrap token; the dashboard issues a per-host token on first contact so a shared secret alone cannot impersonate an existing machine.
  2. Choose a profile — rapid, apt or baseline, each running a different subset of the standard.
  3. Execute modules — technique checks covering malware, credential access, persistence, network behaviour, identity and anti-tamper resilience.
  4. Score and correlate — results are linked by session and mapped to ATT&CK technique IDs, then aggregated across the estate into a comparable posture.
  5. Report — pass/fail counts, an overall score, and a written assessment covering what was caught and what was not.
04

Reading a result

Four outcomes, not two. The middle one is where the useful information lives, and it is the one a binary pass/fail model throws away.

OutcomeMeaningWhat it tells you
PASSTechnique executed, vendor detected and reacted.The control works as advertised on this endpoint.
FAILTechnique executed, no detection at all.A genuine coverage gap. This is the headline finding.
PARTIALDetected, but a later stage of the technique succeeded.Alerting worked; prevention did not. Common and easy to miss.
N/ATechnique does not apply to this endpoint.Not a gap. Scored out rather than counted as a pass.

Every status pairs a colour with a text label — meaning is never carried by colour alone, which would be unreadable to a colour-blind reader and invisible in monochrome print.

05

Surviving the test

An agent that measures tamper resilience must itself be hard to tamper with — otherwise the product under test simply removes the instrument and the run reports nothing. Protection is layered, because each layer assumes the one below it can be defeated:

  • Locked service descriptor — the service denies stop, reconfigure and delete to SYSTEM, so a SYSTEM-level product cannot quietly disable it.
  • Aggressive recovery actions — the service manager restarts it on a short escalating schedule, including after a non-crash termination, which is what a kernel-level kill produces.
  • Guardian service — a second service restarts the first, recreates its registration if deleted, restores its start type, and restores the binary from a backup copy if it is removed.
  • Scheduled tasks — a tertiary safety net running a repair command.

A deliberate uninstall removes the guardian and tasks first, so the framework never fights an operator who is actually trying to remove it.

06

Limitations and out of scope

A framework that reports only strengths is a marketing asset. These are the things it does not do:

  • It measures detection on a single endpoint under a known profile — not coverage across a whole estate, and not adversarial evasion by a sophisticated actor.
  • A passing run means the technique executed and was caught that time. It is evidence, not proof of a guarantee.
  • Self-protection raises the bar for a user-mode actor only. A kernel-mode product can still terminate the agent; recovery layers mitigate, they do not prevent.
  • Scoring weights are opinionated. They are a defensible default, not a standard, and are meant to be edited in the design/ layer.
  • This is a POC framework. It is not hardened for hostile-environment deployment and has not been through an external security review.
