EDR/XDR Module‑Driven Assessment — Proof of Concept

01
The Problem

Most endpoint security products claim to "detect and resist" adversary techniques, but operators have no independent way to verify what actually stops at the endpoint. AgentIde fills this gap with a module‑driven assessment that maps every result to MITRE ATT&CK, producing auditable severity scores, findings, and reports — all without model generation.

A detection is not the same as a prevention. Two products can both show "blocked" for the same technique while behaving completely differently at the edges — one ignores the credential‑theft path entirely, the other survives it.

02
Architecture
  • Agent — Windows service, Go runtime, kernel‑mode resistant hooks. Discovers installed security vendors, executes assessment modules, streams every result back over a WebSocket.
  • Dashboard — React 19 + TanStack Start SSR in a Cloudflare Worker. Aggregates results across the estate, scores findings against ATT&CK techniques, and generates narrative assessment reports.
  • Design — The assessment standard itself as data — which techniques run, how they are weighted, how a pass is defined. Separating this from the code means the standard is reviewable on its own.

Every file a module creates is reported back with its full path. That is deliberate — "we detected it" and "we know exactly what it touched" are different guarantees, and only the second is auditable after the fact.

03
How an Assessment Runs
  1. Deploy the agent — installed as a SYSTEM‑level service with a bootstrap token; the dashboard issues a per‑host token on first contact so a shared secret alone cannot impersonate an existing machine.
  2. Choose a profile — rapid, apt or baseline, each running a different subset of the standard.
  3. Execute modules — technique checks covering malware, credential access, persistence, network behaviour, identity and anti‑tamper resilience.
  4. Score and correlate — results are linked by session and mapped to ATT&CK technique IDs, then aggregated across the estate into a comparable posture.
  5. Report — pass/fail counts, an overall score, and a written assessment covering what was caught and what was not.

06
What the Agent Can Do
  • Execute MITRE ATT&CK‑mapped assessment modules against the endpoint and report results with result, severity, and MITRE mapping per module
  • Export structured findings as HTML, Markdown, JSON, or Docx — using the same deterministic renderer the screen shows, so two exports of one run are byte‑identical
  • Deploy as a SYSTEM‑level service that resists removal — the service descriptor denies stop, reconfigure and delete to SYSTEM, so a SYSTEM‑level product cannot quietly disable it
  • Include AMSI/ETW disabling modules for technique fidelity — ensuring the assessment measures what the technique actually does, not a sanitised version
  • Built‑in watchdog for resilience — restarts the service on crash, including after a kernel‑level kill, with a short escalating recovery schedule
  • Guardian service — a second service restarts the first, recreates its registration if deleted, restores its start type, and restores the binary from a backup copy if it is removed
  • Dual‑use: only use on systems you own or have written authorisation to test
07
Limitations & Out of Scope
  • It measures detection on a single endpoint under a known profile — not coverage across a whole estate, and not adversarial evasion by a sophisticated actor
  • A passing run means the technique executed and was caught that time. It is evidence, not proof of a guarantee
  • Self‑protection raises the bar for a user‑mode actor only. A kernel‑mode product can still terminate the agent; recovery layers mitigate, they do not prevent
  • Scoring weights are opinionated. They are a defensible default, not a standard, and are meant to be edited in the design/ layer
  • This is a POC framework. It is not hardened for hostile‑environment deployment and has not been through an external security review
